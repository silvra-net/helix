# Installing Helix

> Part of the [Helix documentation](../README.md).

## Installation

### System Requirements

| Resource | Minimum | Recommended | Notes |
|---|---|---|---|
| **CPU** | 1 vCPU | 2+ vCPU | Producing and checking a block every two seconds is cheap. Headroom matters when the node also serves a busy public API. Proof-of-personhood proofs are generated by the client, not the node. |
| **RAM** | 1 GB | 2 GB | Run the node with `MALLOC_ARENA_MAX=2` — without it glibc keeps freed memory per thread and a node grew to 3 GB in four days; with it memory stays flat (a few hundred MB, up to about 1 GB after long uptime). See [Running a Node](running-a-node.md#running-a-node). |
| **Disk** | 10 GB free | 30 GB+ | The chain database grows with every block: about 17 KB for an empty block, about 47 KB per block on the previous testnet chain (4–6 validators, light traffic) — roughly 2 GB a day at one block every two seconds. **Cap it** with `HELIX_KEEP_BYTES` (for example `20G`) or `HELIX_KEEP_BLOCKS`; the node then deletes old blocks and the file stops growing. Below 1 GiB of free space the node stops writing and exits with its database intact (Linux and macOS). |
| **Network** | Outbound HTTPS (443) | P2P port 8546 open inbound | A node needs only outbound connections: it joins through the public seed over HTTPS/WSS, behind NAT and firewalls alike. A validator should open **8546/tcp** if it can — every validator the others can reach directly takes load off the public hub, and the network no longer depends on that one link. The REST API listens on `127.0.0.1:8545`; serve it publicly only through a reverse proxy. |
| **OS / Arch** | Linux x86_64, macOS (Apple Silicon), Windows x86_64 | — | The platforms each release is built for. Others need a source build and are untested. |

Watch the disk rather than trusting a table: `GET /diagnostics` on your node reports the
database size, bytes per block and — without a cap — how many days of free space are left.

### Option A: Download a Release

Every release on the [Releases page](https://github.com/silvra-net/helix/releases) carries:

- **Command line and node:** `helix-cli-<version>-linux-x86_64.tar.gz`,
  `helix-cli-<version>-macos-arm64.tar.gz`, `helix-cli-<version>-windows-x86_64.zip` — one
  `helix` binary that is both the node (`helix start`) and the client.
- **Desktop wallet:** `helix-gui-<version>-linux.AppImage`, `.deb`, `.rpm`,
  `helix-gui-<version>-macos-arm64.dmg`, `helix-gui-<version>-windows.msi` or `.exe`. It bundles
  the same `helix` binary to run a node.

Extract the archive and run `helix` — no Rust toolchain needed. **The public network runs the
latest release**; a newer build from `master` may follow rules the network does not have yet.

### Option B: Build From Source

Prerequisites:

```bash
# Rust (stable)
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
source "$HOME/.cargo/env"

# System libraries (Ubuntu/Debian)
sudo apt-get install pkg-config libssl-dev
```

Build the latest release tag:

```bash
git clone https://github.com/silvra-net/helix.git
cd helix
git checkout v0.20.3
cargo build --release
# target/release/helix — the node (`helix start`) and the client (`helix wallet`, `helix tx`, …)
```

The desktop wallet needs more system libraries (WebKitGTK on Linux); see [`gui/`](../gui/README.md).

### Upgrading

Stop the node, replace the binary, start it again. When a release **starts a new chain**, its
release notes say so and give the steps: the old chain database has to be renamed first — the new
build refuses to start on it, and says which file to rename. Keep `validator-key.json` and
`validator-key.signing-state.json`; the key is your validator on the new chain too.

A chain database can always be rebuilt from the network: rename it (do not delete it) and start
the node, and it syncs the chain again.
